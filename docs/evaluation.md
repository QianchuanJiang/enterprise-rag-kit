# 场景达标标准与数据方案（三个场景共用基线）

> 本文回答两个前置问题：(1) 场景要应对程序员客栈等级面试 / 作品审核，要做到什么程度；(2) RAG 的数据从哪里来、有没有办法。
> 结论：等级面试对"作品"的要求恰好与"可信 + 代码具体 + 可查 Git"一致；数据来源完全有办法，且分三条路线。

---

## 一、场景要应对什么：程序员客栈等级面试 / 作品审核

**已核实的机制**
- 平台采用 **技术等级认证 T1–T5**，由 **1V1 视频面试**定级，面试官为 6 年以上大厂、年薪 50 万+ 的技术专家。
- 认证考察三块：**身份信息 + 薪资验证 + 专业技术面试**。其中「项目经验」明确来自「您在程序员客栈绑定的**个人代表性作品**」，平台鼓励「上传 Git 帐号 / 用 Git 服务网站进行作品展示」。
- 各等级标准（节选）：T2 熟练级 = 熟练独立开发常见应用；**T3 专业级 = 解决复杂问题、技术全面、具备一定架构设计思维**。

**这意味着什么**
- 场景仓库不是给客户看的炫技 demo，而是**面试官评判你「项目经验 + 架构思维」的直接证据**。他会读代码、看结构、挑谎。
- 以你的背景，应瞄准 **T3 专业级**：仓库必须清晰展现架构判断力，而不只是"能跑"。

## 二、场景要做到什么程度（质量基线）

### MUST（必须满足）
1. **生产级参考实现**，不是 notebook 片段：模块化、单一职责、配置驱动、有错误处理与降级。
2. **端到端可运行**：一条命令入库、一条命令问答（现有脚手架已具备该形态）。
3. **真实指标**：在真实（小规模）数据上跑出真实数字——哪怕只有 8 份年报、50 条标注，也比空泛宣称有力。
4. **诚实**：明确标注"哪些是真实能力、哪些是示意 / stub"。资深面试官一眼能看穿编造的数字，那会比没有指标更减分。
5. **可复现的评测**：RAGAS 或近似指标 + 对照实验脚本，别人能重跑。

### NOT（不必做）
- 已上线 SaaS、真实用户量、超高复杂度工程。**面试官看的是工程判断力信号，不是生产流量。**

### Git 仓库验收清单（逐条对照）
- [ ] README：问题定义、架构图、快速开始、指标表、对照实验、已知限制
- [ ] 代码结构：config / parsers / chunking / retrieval / generator 分层，单一职责
- [ ] 可运行：`ingest` + `ask` 一键跑通（含轻量后端，零模型下载也能演示）
- [ ] 测试：pytest 至少覆盖解析降级、ACL 拦截、无据拒答
- [ ] 评测：指标脚本可复现，对照实验（纯向量 → +BM25 → +重排 → +改写）
- [ ] 数据：提供下载脚本 + 抽样说明；**不把大 PDF 塞进 Git**（用 .gitignore + 外部下载）
- [ ] 合规：LICENSE、数据来源声明、现东家资产零出现

## 二·补、面试场景"数据真实性"与"指标真实性"必须分开看

**用户洞察（已确认）**：面试场景不必、也**不应**使用真实企业机密数据。这恰好是对的，原因在于三点——

1. **合规红线**：真实客户文档含商业秘密 / 知识产权，一旦公开到 Git 即构成泄露，且通常受 NDA 约束。用真实数据做公开场景是自找麻烦。
2. **脱敏是额外负担**：若用真实数据，脱敏（PII / 密级遮蔽）本身是一项不可逆的信息损耗工程，对"演示"毫无增益。
3. **面试官要的是工程能力信号，不是某家企业内部文档**：T3 考察的是你解决复杂问题、做架构设计的思维，不考察你是否手握某公司的保密资料。

**因此：场景数据用「公开 + 合成」是正确且主流的做法**（我们三个场景已如此设计），完全不需要"那么真实"。但要严格区分两个维度：

| 维度 | 是否要求"真实企业数据" | 真正要求是什么 |
|---|---|---|
| **数据真实性**（data authenticity） | 不要求。公开年报 + 合成密级标注 足够且更优 | 来源合法、可开源、无 IP 风险 |
| **指标真实性**（metric authenticity） | — | **必须真实**——用你提交的评测脚本，在你提交的（公开/合成）数据上**真实跑出来**，且别人能复现 |

**致命陷阱（务必规避）**：数据既然是合成的，便顺手编一个漂亮指标。这叫"双重伪造"，比没有指标更致命——资深面试官会要求复现，编的数字一跑就穿帮。**合法组合 = 合成/公开数据 + 真实跑出的指标**；**自毁组合 = 合成数据 + 编造指标**。

**脱敏的真实位置**：它是**实际接单项目**的交付项（摄入客户真实文档时必须做 PII/密级脱敏，且你在 NDA 下作业）。场景阶段通过"不用真实数据"直接绕开。但你可把脱敏做成管道内的**功能模块**（自动遮蔽身份证/手机号/金额）——这叫"演示脱敏能力"，是加分项而非负担。

## 三、数据从哪里来（有办法，三条路线）

### 路线 1 · 真实公开年报 / 招股书（场景 A）
- **来源**：巨潮资讯网 cninfo 公开 AJAX 接口（`/new/hisAnnouncement/query`），无需登录 / 付费 / 验证码，返回 PDF 直链；社区已有 cninfo-mcp、开源爬虫可直接用。
- **合规**：标注来源、请求限流、不商业再分发；技术验证用途合法。
- **规模**：**5–10 份**即可产出真实指标，不必凑 50 份。

### 路线 2 · 真实公开法规（场景 B 的内容）
- **来源**：国家法律法规数据库 `flk.npc.gov.cn`，公开可获取。
- **关键限制**：真实法规**没有密级标签**。B 的分级权限 / 审计必须**在真实内容上做合成标注**（构造 public / internal / restricted + 三角色），这是 B 的必要组成，不是偷懒。

### 路线 3 · 合成但拟真的文档（场景 B 的 ACL 演示 / 安全兜底）
- 自己撰写一份"内部制度手册"样张，自带密级标签：零版权风险、完全可控、便于确定性评测。
- 当真实数据获取受阻时的兜底，也是演示 ACL 最干净的方式。

### 计算资源现实
- 完整链路（docling + BGE-M3 + reranker + LLM）对算力要求高。
- **开发期用轻量后端**（已建 fake 向量 + stub 生成器，零下载可端到端跑）；正式指标在 modest 环境跑一次、如实记录即可。

## 四、对 A / B / C 的数据与达标影响（小结）

| 场景 | 数据路线 | 达标要点 |
|---|---|---|
| A 异构解析 | 路线 1（5–10 份年报） | 真实解析/检索/问答指标 + 对照实验表 |
| B 合规权限 | 路线 2 内容 + 路线 3 合成密级（必须） | 越权拦截 100% + 三角色演示 + 审计链 |
| C 离线私有化 | 复用 A/B 数据 | 只换部署形态（docker compose + 断网自测） |
| 评测集 | 用户人工标注 | 50 QA + 30 拒答样本，与数据来源无关 |

> 一句话：**数据有办法，且恰好分三层对应三个场景；等级面试要的"可信 + 代码具体 + 可查 Git"，与我们定的生产级参考实现基线完全一致——这不是额外负担，是同一件事。**
