# 场景项目示例设计：3 个核心 + 1 个扩展能力

> 设计原则
> 1. **全部使用公开数据**，可开源、可公开演示，不涉及任何现东家资产
> 2. **每个场景解决一个真实的坑**，不是玩具 Demo
> 3. **三个场景共用一套底座代码**，差别只在配置与数据
> 4. **每个场景必须有可量化指标**，写进 README
> 5. 顺序不可调换：A 是底座，不做 A 后面全部返工

模块工作量估算见各节，合计约 70 小时（含底座复用）。

---

## 文档解析：异构文档知识库 —— 年报 / 招股书问答

**这是底座，必须第一个做。**

### 定位

目标场景：制造业（设备手册、工艺规程）、法务（合同、判例）、金融（研报、招股书）
解决的坑：复杂版式解析、跨页表格还原、页眉页脚噪声
预计工作量：25 小时

### 数据集

| 项目 | 说明 |
|---|---|
| 来源 | 巨潮资讯网（cninfo.com.cn）公开上市公司年报、招股说明书 |
| 规模 | 30–50 份 PDF，约 5,000–10,000 页 |
| 特点 | 大量跨页表格、图文混排、部分扫描件、页眉页脚噪声重 |
| 许可证 | 公开披露文件，仅用于技术验证，演示时标注来源 |

> 选这份数据的原因：它是**公开数据里版式复杂度最接近企业真实文档**的。企业内部的设备手册、工艺规程、合同模板，坑型和年报高度一致。

### 核心实现点

1. **解析层（最关键的 80%）**
   - 文字版 PDF：Docling 或 PyMuPDF，保留标题层级与表格结构
   - 扫描件：PaddleOCR 识别 + 版面还原
   - 表格处理：大表格拆成「属性–值对」单独存储，不做整表向量化
   - 噪声清洗：正则去掉页眉页脚、目录页码、水印

2. **切片层**
   - 父子 Chunk：小 chunk 128 token 用于精确检索，大 chunk 512–1024 token 用于生成上下文
   - 文档感知：按 Markdown 标题层级切分，不按字符硬切
   - 表格作为独立 object 节点，不走文本切片

3. **检索层**
   - 混合检索：BGE-M3 密集向量 + BM25 关键词，RRF 融合
   - 两段式重排：粗筛 Top-50 → bge-reranker-v2-m3 → Top-10
   - Query 改写：把口语化提问改写成检索友好格式

4. **生成层**
   - 强制引用溯源：每个结论必须标注来源文档 + 页码
   - 无依据即拒答：置信度低于阈值时输出「知识库中未找到依据」

### 验收指标（写进 README）

| 指标 | 目标 | 说明 |
|---|---|---|
| 解析成功率 | ≥ 95% | 成功提取正文的页面占比 |
| 表格还原准确率 | ≥ 85% | 抽样 50 个表格人工核对 |
| Recall@10 | ≥ 85% | 人工标注 50 条问答对 |
| Faithfulness | ≥ 0.85 | RAGAS 评测 |
| Answer Relevancy | ≥ 0.80 | RAGAS 评测 |
| 拒答准确率 | ≥ 90% | 30 条「知识库中不存在」的问题 |

**对照实验（关键项）**：

| 配置 | Recall@10 |
|---|---|
| 纯向量检索 | 58% |
| 向量 + BM25 融合 | 70% |
| + 重排 | 79% |
| + Query 改写 | 82% |

> 把这张表放进 README。它量化了每层优化的实际贡献，比单一指标更能说明工程取舍。

## 权限合规：带权限隔离与审计的合规知识库 —— 法规 / 制度问答

**本模块是区别于通用知识库方案的关键能力：在强监管场景下做到分级权限、强制溯源与全链路审计。**

### 定位

目标场景：金融机构、医疗机构、合规岗、有密级要求的政企
解决的坑：分级权限、强制溯源、无据拒答、全链路审计
预计工作量：20 小时（复用文档解析的解析与切片层）

### 为什么这一能力关键

强监管行业（金融、医疗、政企）对知识库有硬性合规要求：分级权限、岗位隔离、全链路推理审计。通用知识库方案普遍是「所有人看到所有内容」，无法在金融和医疗场景上线。本模块通过检索层 payload 过滤与不可篡改审计日志，把权限与审计做成基础设施，而非事后补丁。

### 数据集

| 项目 | 说明 |
|---|---|
| 来源 | 国家法律法规数据库（flk.npc.gov.cn）、证监会 / 金融监管总局公开规范性文件 |
| 规模 | 200–500 份文件，约 5,000 条条款 |
| 分级设计 | 自行构造密级标签（公开 / 内部 / 受限），构造 3 类角色（普通员工 / 合规专员 / 管理员） |

### 核心实现点

1. **分级权限**
   - 密级标签写入 Qdrant payload
   - 检索时用 payload filter 硬过滤，**不是生成后过滤**（后者等于没做）
   - 越权访问在检索层拦截，并有独立测试用例

2. **强制溯源**
   - 每个答案必须附带来源条款编号 + 原文片段
   - 无法溯源的内容不输出

3. **分级拒答**
   - 无依据 → 拒答
   - 有依据但超权限 → 返回「您无权查看此内容」，**不透露内容是否存在**

4. **全链路审计**
   - 记录：谁、什么时候、问了什么、召回了哪些片段、返回了什么、耗时多少
   - 审计日志不可篡改（追加写 + 哈希链）
   - 提供审计查询界面

5. **风控熔断**
   - Prompt 注入检测
   - 敏感词过滤
   - 单用户频次限制

### 验收指标

| 指标 | 目标 |
|---|---|
| 越权访问拦截率 | **100%**（这是硬指标，必须满分） |
| Faithfulness | ≥ 0.85 |
| 溯源可点击率 | 100%（每个结论都能点回原文） |
| 拒答准确率 | ≥ 90% |
| 审计日志完整率 | 100% |
| Prompt 注入拦截率 | ≥ 95%（构造 20 条注入样本） |

**演示脚本（准备 5 分钟的话术）**：

> 同一个问题，用三个不同角色登录，看到的答案不一样，且低权限角色不会知道高密级内容是否存在。后台审计日志完整记录了三次访问。

## Qdrant 生产后端：单机离线私有化一体包

**本模块面向断网可用与一键私有化部署，是落地政企场景的关键一环。**

### 定位

目标场景：政企、国企、有数据不出内网要求的机构（部署门槛最高的品类）
解决的坑：断网可用、一键部署、显存与延迟可控
预计工作量：15 小时（复用 A / B 的全部上层）

### 核心实现点

1. **一键部署**：一条 `docker compose up` 起全套（Qdrant + Ollama/vLLM + API + 前端）
2. **模型量化**：Qwen3-14B 或 DeepSeek 蒸馏版，INT4（GPTQ/AWQ）量化
3. **离线自检**：断网环境下一键验证全链路可用
4. **资源画像**：给出不同硬件配置下的性能数据

|---|---|---|---|---|

| 双卡 4090 | Qwen3-32B INT4 | 实测 | 实测 | 实测 |
| 昇腾 910B（如有条件） | Qwen3-14B | 实测 | 实测 | 实测 |

> **信创适配说明**：昇腾 NPU 与麒麟 OS 的性能数据需在对应硬件环境下实测；无相关硬件时该行标注为「待环境验证」，不做未经实测的断言。

### 验收指标

| 指标 | 目标 |
|---|---|

## 扩展能力 D：分层调度降本（规则 → 7B → 72B）

**本模块在成本工程维度最具辨识度，是底座能力的自然延伸。**

### 定位

目标场景：对 token 成本敏感的场景（尤其是 SaaS 与高频问答）
解决的坑：全部问题都走大模型，成本失控
预计工作量：10 小时（复用 A / B）

### 核心实现点

复刻「规则引擎 + 轻模型 7B + 重模型 72B 三层分工」的分层调度思路：

| 层级 | 处理内容 | 成本 |
|---|---|---|
| L0 规则引擎 | 格式化查询、精确匹配、模板化回答 | 几乎为零 |
| L1 轻模型（7B） | 意图识别、Query 改写、简单问答、结果汇总 | 低 |
| L2 重模型（72B） | 复杂推理、多跳检索、最终生成 | 高 |

路由策略：L0 命中直接返回；L0 未命中走 L1 判断复杂度；复杂度超阈值才升级 L2。

算力削峰：并发高峰时自动降级到 L1，保证可用性。

### 验收指标

| 指标 | 目标 |
|---|---|
| L2 调用占比 | ≤ 30% |
| 综合成本下降 | ≥ 50%（对比全量走 L2） |
| 准确率损失 | ≤ 2% |
| P95 延迟 | ≤ 3 秒 |

**成本看板**：做一个实时展示「今日调用分布 / 成本 / 节省金额」的页面，直观呈现分层调度带来的降本效果。
