# 权限合规 · 企业知识库权限审计与越权拦截（合规 Guard）—— 功能清单与验收标准

> 文档性质：**需求与功能层**，不含实现细节。
> 阶段定位：3 个核心场景之一（A/B/C）。A（解析）已完成；本步只定 B 的功能与验收；C（离线私有化）后续单独定。
> 决策记录：场景数量 = 3 核心（A/B/C）；B 的差异化锚点 = **检索层硬拦截 + 全量审计**，而非"生成后遮挡"；数据来源 = 合成（因真实 PDF 下载在本环境被服务端拦截，沿用"数据可合成、指标必须真实跑出"原则）。

---

## 1. 定位与目标目标用户

| 项 | 内容 |
|---|---|
| 一句话价值 | 让企业知识库「不该看的人看不到、谁看了有迹可查」——把数据安全做成可验证的工程能力，而非一句承诺 |
| 目标目标用户 1 | 政企 / 金融机构信息化部（密级文档、合规审计是硬指标） |
| 目标目标用户 2 | 上市公司证券事务 / 法务（内幕信息、未公开经营数据需最小权限） |
| 目标目标用户 3 | 大型制造 / 能源集团（工艺、配方、供应商合同分级管控） |
| 差异化锚点 | **检索层就拦截**（低权限用户根本检索不到受限片段），而非生成后遮挡；外加**全量审计日志**——这两点是通用 RAG 方案普遍缺失、却是企业必问的 |

> 为什么是 B 的关键能力：多数开源 RAG Demo 的"权限"只是生成时把答案打码，底层向量库里受限文本人人可检索，等于没防护。B 把 ACL 做进**检索层**（`can_access` 在 `retriever.search` 内直接调用，上层无法绕过），并提供**谁问了什么、命中哪些密级、是否越权尝试**的审计记录——这才是能通过合规审计的方案。

## 2. 数据来源与合规

| 项 | 说明 |
|---|---|
| 来源 | 合成语料（与 A 同源的跨行业年报风格文本），按密级打标 |
| 密级体系 | `public`（公开财务数据）/ `internal`（内部经营计划、未披露预算）/ `restricted`（未公开并购、核心配方、内幕信息）三级 |
| 规模 | 8 家跨行业 × 每家的公开/内部/受限三类片段，约 40–60 chunks |
| 特点 | 同一份语料里天然混布三种密级，便于演示「同一问题、不同身份、不同可见范围」 |
| 合规红线 | 不得包含任何现东家资产、客户数据、架构图；合成数据仅用于技术验证 |

## 3. 功能清单（需求级）

### 模块 1 · 接入与密级标注
- **F1.1 入库即打标**：`ingest` 阶段为每个 chunk 打 `acl_level`，缺省取 `security.default_level`
- **F1.2 密级可配置**：密级来源于文档元数据或配置映射，支持与企业既有 IAM/钉钉/企微角色对接（本期以配置演示，预留对接点）
- **F1.3 容错降级**：单文档密级缺失时按默认级处理并记入审计，不中断整批

### 模块 2 · 检索层硬拦截（B 的立身之本）
- **F2.1 检索即过滤**：`retriever.search` 内部调用 `can_access(user_level, chunk.acl_level)`，低权限用户**根本不会拿到**受限片段的向量与文本
- **F2.2 不可绕过**：ACL 在检索层生效，上层问答/生成无法读取被拦截内容（与"生成后遮挡"有本质区别）
- **F2.3 可解释拒因**：被拦截时返回明确信号（`refused` + `reason=acl`），前端可提示"无权限访问该信息"

### 模块 3 · 审计日志
- **F3.1 全量记录**：每次 `ask` 落一条审计：`user` / `user_level` / `question` / `命中密级集合` / `是否越权尝试` / `时间戳`
- **F3.2 越权标记**：低权限用户试图命中受限内容时，审计标记 `denied=true`
- **F3.3 可查接口**：提供 `/audit` 端点（生产需鉴权）与 CLI 导出，供合规抽查

### 模块 4 · 越权自检
- **F4.1 acl_selfcheck**：输入问题，返回各密级可见 chunk 数，用于上线前自检"是否漏标/错标"
- **F4.2 分级问答**：支持以指定 `user_level` 发起查询，演示不同身份的差异

### 模块 5 · 问答（复用 A 底座）
- **F5.1 强制溯源**：在权限范围内，每个结论标注来源 + 页码
- **F5.2 无据拒答**：检索置信度低于阈值时拒答（与 A 同源的 `guard.refuse_threshold`）

### 模块 6 · 评测与证据
- **F6.1 越权拦截率**：低权限用户问受限问题，受限 chunk 命中数应为 0
- **F6.2 最小权限率**：用户可见 chunk 的 `acl_level` 全部 ≤ 自身级别
- **F6.3 审计覆盖率**：100% 查询产生审计记录，越权尝试 100% 标记
- **F6.4 正常可用性**：管理员视角复用 A 的 Recall@5 / 溯源 / grounding 指标，证明"加了权限不牺牲可用性"

## 4. 验收标准（可量化）

| 编号 | 维度 | 指标 | 目标值 | 测量方式 |
|---|---|---|---|---|
| AC-1 | 越权拦截 | 低权限用户问 `restricted` 内容时，受限 chunk 命中数 | = 0 | 评测脚本断言 `can_access` 过滤后集合为空 |
| AC-2 | 最小权限 | 返回 chunk 的 `acl_level` 全部 ≤ 用户级别 | 100% | 比对每用户级别与命中密级 |
| AC-3 | 审计覆盖 | 每次 `ask` 产生审计记录 | 100% | 统计审计条数 = 查询数 |
| AC-4 | 越权可溯 | 被拦截查询在审计中标记 `denied=true` | 100% | 检查 `denied` 字段 |
| AC-5 | 可用性 | 管理员视角 Recall@5 | ≥ 95%（复用 A 真实指标） | 同 A 评测集 |
| AC-6 | 自检 | `acl_selfcheck` 正确报告各密级可见数 | 通过 | 脚本断言输出与配置一致 |
| AC-7 | 正常拒答 | 无据问题正确拒答（不泄漏受限内容） | ≥ 90% | 30 条越权/无据样本 |

> **AC-1 的关键**：它证明防护发生在"数据出口"（检索层）而非"答案出口"（生成后）——后者底层受限文本仍可被检索到，等于没有真正防护。

## 5. 范围边界

**本阶段含**：模块 1–6 全部功能 + 上述 7 条验收标准（在合成密级语料上跑出真实可复现指标）。

**本阶段不含**（属其他场景，避免返工）：
- 异构文档深度解析（跨页表格 / OCR）→ 文档解析（已完成）
- 离线私有化部署 / 信创（昇腾 + 麒麟）适配 → Qdrant 生产后端
- 分层调度降本（规则→7B→72B）→ 可选 D
- 与企业真实 IAM/SSO 对接 → 预留接口，本期以配置映射演示

**与 A/C 的衔接**：B 复用 A 的解析 / 切片 / 检索 / 生成底座，仅新增 `SecurityConfig`（`acl_enabled` / `audit_enabled` / `default_level`）、`AuditLogger`、`can_access`、以及 `/audit` 与 `acl_selfcheck`。C 的 Qdrant 后端起来后，ACL 过滤可下沉为 **payload 条件检索**（检索层即带密级过滤，性能更优），B 的逻辑不变。

## 6. 技术栈与算力（摘要，详见《场景技术栈与算力说明》）

| 层 | 选型 | 说明 |
|---|---|---|
| 嵌入 | 本地 Ollama `bge-m3`（1024 维） | 零成本、数据不出域，与 A 同源 |
| 生成 | 智谱 GLM-4.6V-Flash（OpenAI 兼容） | 免费档、128K、可溯源，与 A 同源 |
| 权限 | `can_access` 检索层硬过滤 + `AuditLogger` | 底座已就位，B 仅做配置与演示收口 |
| 审计存储 | 本地 `audit.jsonl`（一行一查） | 零依赖，生产可换数据库 |
| 算力 | 本机（Ollama + 智谱 API） | 与 A 一致，无需新增硬件 |
