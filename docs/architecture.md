## 1. 背景与问题定义

企业内部的专有知识长期"搜不到、答不准"：文档散落在共享盘、OA、企微、邮件，全文搜索只能做关键词匹配；而通用大模型又不能直接用于企业私有数据——它没见过企业内部资料、会一本正经地编造、且数据不允许出内网。**RAG（检索增强生成）是当前唯一成本可控的解法**，但"接个 ChatGPT 就是知识库"是普遍误解，真实落地有三道坎，且每道坎都对应一个同类方案稀少的能力断层：

1. **文档解析**：真实企业文档是扫描件、跨页大表、带页眉页脚的噪声 PDF，通用方案一解析就乱。
2. **合规可信**：金融/医疗/政企要求"不同角色看不同密级、操作可追溯"，95% 的玩家做不出。
3. **私有化与信创**：政企要求数据不出内网、还能跑在昇腾+麒麟上；集成商因交付规模小而通常不承接，能做的人极少。

本框架即围绕这三道坎构建可复用的交付能力。

## 2. 核心概念边界：知识库 vs 智能体

这是定位的底层问题，必须先厘清。**知识库（RAG）本身不是智能体**，二者是不同抽象层级：

- **知识库 / RAG**：被动问答系统——提问 → 检索私有文档 → 生成带引用的答案。无自主行动能力。
- **智能体 / Agent**：带"感知—规划—记忆—行动"闭环的系统，LLM 当大脑做决策，通过工具（tool）调用数据库/搜索/API/代码来**自主推进目标直至把事办完**。

二者关系有三种（也是本框架的演进路径）：

| 关系 | 说明 | 对应形态 |
|---|---|---|
| RAG 是 Agent 的组件 | Agent 把知识库当"查资料"的工具调用 | 企业智能体 = RAG + 工具集 |
| 加"规划+工具+行动"编排 | 在知识库上叠加自主编排层即升级为 Agent | 从蓝框到紫框 |
| 中间态 Agentic RAG | 检索本身变聪明：自主决定何时检索、多跳检索、反思后补检索 | 介于二者之间 |

**本框架与三个场景的定位：处于"引擎层 / 地基"**——即 RAG 这一层，是任何企业智能体都绕不开、且最难、最值钱的那块。本框架的定位是"**企业智能体的知识中枢 / RAG 引擎**"，并保留升级为端到端智能体的空间。是否单独构建完整 Agent 编排层？**先把检索地基做扎实**，Agent 编排作为后续扩展能力。

## 3. 产品定位与命名体系

为体现"架构设计思维"，三个场景不做成孤立 demo，而是**同一套框架下的三次递增交付**——底座（解析/检索/问答/评测）一次写好，三个场景只换配置与上层能力。

| 层级 | 名称 | 仓库名 | 一句话定位 |
|---|---|---|---|
| 框架 | **「知擎」企业级 RAG 引擎** | `enterprise-rag-kit` | 可复用的企业知识库底座，支撑三类交付场景 |
| 文档解析 | **知擎·解析** DocParse | `rag-kit/` | 把最难解析的企业文档做对，回答可溯源 |
| 权限合规 | **知擎·合规** Guard | `rag-kit/src/permissions.py` | 分级权限 + 不可篡改审计（同类方案较少） |
| Qdrant 生产后端 | **知擎·信创** Edge | `rag-kit/configs/tenant_c.yaml` | 断网可用、一键部署、跑在信创环境（部署要求最高） |
| 分层调度（可选） | **知擎·调度** Router | `rag-kit/src/router.py` | 规则→小模型→大模型三级路由，降低推理成本 |

中文产品名负责"讲给人听"，代码位置负责"查实现"。三个模块共用同一底座，通过配置与上层能力按需启用。

## 4. 设计目标与约束（质量基线）

### 4.1 质量基线：MUST / NOT
**MUST**
1. 生产级参考实现（模块化、单一职责、配置驱动、有错误处理与降级），非 notebook 片段。
2. 端到端可运行：一条命令入库、一条命令问答（含轻量后端，零模型下载也能演示）。
3. 真实指标：在真实（小规模）数据上跑出真实数字——哪怕 8 份年报、50 条标注。
4. 诚实：明确标注"哪些是真实能力、哪些是示意/stub"。编造数字比没有指标更致命。
5. 可复现评测：RAGAS 或近似指标 + 对照实验脚本，别人能重跑。

**NOT**：已上线 SaaS、真实用户量、超高复杂度工程。评测关注的是工程判断力信号，不是生产流量。

### 4.2 两个真实性必须分开
| 维度 | 是否要真实企业数据 | 真正要求 |
|---|---|---|
| 数据真实性 | 不要求（公开+合成更优） | 来源合法、可开源、无 IP 风险 |
| 指标真实性 | — | 必须真实——提交的评测脚本，在（公开/合成）数据上真实跑出，且可复现 |

**致命陷阱**：数据合成便顺手编漂亮指标（"双重伪造"），评测方会要求复现，一跑即穿帮。合法组合 = 合成/公开数据 + 真实指标；自毁组合 = 合成数据 + 编造指标。

### 4.3 算力约束
A/B 可全走 API（硅基流动/百炼），本机只需 Python+Docker，零本地 GPU；C 必须本地算力（3090/4090 跑 14B，或客户昇腾环境）。详见第 8 章算力总账。

### 4.4 合规边界（贯穿全程）
- 不出现现东家名称、不出现特定行业的具名资产，规避 NDA/竞业风险。
- 信创（昇腾+麒麟）仅作为个人技术能力呈现，不绑定雇主。
- 数据来源必须标注；真实客户文档的脱敏是实际商业化交付项目交付项，场景阶段通过"不用真实数据"绕开。

## 5. 总体架构设计

### 5.1 五层架构
```
┌──────────────────────────────────────────────────────────────┐
│  L5 生成 (LLM)          Qwen3:14B 本地 / Qwen API 在线           │
├──────────────────────────────────────────────────────────────┤
│  L4 重排 (Reranker)     bge-reranker-v2-m3                      │
├──────────────────────────────────────────────────────────────┤
│  L3 向量库 (Vector DB)  Qdrant（compose / 单机，payload 过滤）    │
├──────────────────────────────────────────────────────────────┤
│  L2 嵌入 (Embedding)    BGE-M3（dense + sparse 一体）            │
├──────────────────────────────────────────────────────────────┤
│  L1 解析 (Parsing/OCR)  docling + MinerU + PaddleOCR            │
└──────────────────────────────────────────────────────────────┘
   编排：轻量自研 + Pydantic 配置驱动   服务：FastAPI + Streamlit   部署：Docker Compose
```

### 5.2 模块划分（共享底座 `rag-kit` 雏形）
| 模块 | 职责 | 被哪些场景复用 |
|---|---|---|
| `config` | Pydantic 配置驱动，tenant 级差异 | A/B/C/D |
| `parsers` | 多格式解析、OCR、噪声清洗、表格还原 | A（核心）/ B / C |
| `chunking` | 父子 Chunk、结构感知切片、表格独立节点 | A / B / C |
| `quality` | 解析/表格质量校验与降级 | A |
| `embeddings` | BGE-M3 dense+sparse 一体，可 API/本地 | 全部 |
| `retriever` | 混合检索 + 两段式重排 + 可解释召回 + payload 过滤 | 全部 |
| `generator` | 强制溯源、无据拒答、stub 双模式 | 全部 |
| `permissions` | 分级 ACL、越权拦截、审计链 | B（核心）/ C |
| `router` | 规则→7B→72B 三级路由 | D（核心） |
| `pipeline` | 摄入/问答/审计编排 | 全部 |
| `api` | FastAPI 对外服务（ingest/ask/audit） | 全部 |
| `cli` | 命令行入口 + stub 兜底 | 全部 |
| `eval` | RAGAS 式离线评测 + 对照实验 | 全部 |

### 5.3 底座复用策略
A 是底座，必须先做；B 复用 A 的解析/切片/检索/生成，仅加权限/审计层；C 复用 A/B 全部上层，仅换部署形态；D 复用 A/B 加路由层。**目标：新模块通过配置复用底座，避免重复实现。**

## 7. 三个核心场景设计

### 7.1 文档解析 · 知擎·解析 DocParse
**定位/目标用户**：制造业信息化部（设备手册）、法务（合同/判例）、金融研究（年报/招股书）。证明"通用方案解析错的复杂文档，本项目能做对"。

**数据**：巨潮资讯网（cninfo）公开年报/招股书，5–10 份即可出真实指标（路线 1）。选它是因为公开数据里版式复杂度最接近企业真实文档。

**功能（6 模块）**
1. 文档接入：PDF（文字版+扫描版）、Word、Markdown；批量入库，单文件失败降级不中断整批。
2. 解析质量：跨页表格还原为「属性-值对」；无文字层自动 OCR；页眉页脚/目录页码/水印噪声清洗；标题层级保留。
3. 检索：稠密向量+BM25 混合；两段式重排；Query 改写；可解释召回（来源+命中理由）。
4. 问答：强制溯源（来源+页码）；无据拒答。
5. 评测：解析成功率、表格还原准确率、Recall@k、Faithfulness、拒答准确率；对照实验表（纯向量→+BM25→+重排→+改写 召回率递进）。
6. 文档与复现说明：README 指标表、复现步骤。

**验收标准（完整版见 `文档解析_功能清单与验收标准.md`）**
| 编号 | 维度 | 指标 | 目标 |
|---|---|---|---|
| AC-1 | 解析 | 解析成功率 | ≥ 95% |
| AC-2 | 表格 | 表格还原准确率 | ≥ 85% |
| AC-3 | 检索 | Recall@10 | ≥ 85% |
| AC-4 | 生成 | Faithfulness | ≥ 0.85 |
| AC-5 | 生成 | Answer Relevancy | ≥ 0.80 |
| AC-6 | 拒答 | 拒答准确率 | ≥ 90% |
| AC-7 | 对照 | 纯向量召回递进 | 58% → 82% |

> AC-7 的工程价值：用对照实验量化「解析质量对召回的影响」以及每层优化的实际贡献。

**范围边界**：含模块 1–6 + 上述 7 条；不含权限/审计（B）、离线私有化/信创（C）、分层调度（D）。

### 7.2 权限合规 · 知擎·合规 Guard
**定位/目标用户**：金融、医疗、政企合规岗。证明"多数通用方案做不出的分级权限+审计，本项目能够实现"。

**数据**：路线 2（国家法律法规数据库 flk.npc.gov.cn 真实公开）+ 路线 3（自写带密级标签的"内部制度手册"样张，零版权风险）。**真实法规无密级标签，合成密级标注是 B 的必要组成，非偷懒。**

**功能**
1. 分级权限模型：public/internal/restricted 三级 + 三角色（访客/员工/管理员）。
2. 越权拦截：基于密级标签的检索/问答级访问控制，在检索层 payload 硬过滤（非生成后过滤），越权拦截率 100%（测试用例覆盖）。
3. 三角色演示：同一问题不同角色看到不同密级答案。
4. 强制溯源 + 无据拒答（复用 A 基线）。
5. 操作审计：不可篡改审计日志（谁/何时/问了什么/命中哪些片段/是否被拦截），追加写+哈希链。
6. 风控熔断：Prompt 注入检测、敏感词过滤、频次限制（加分）。

**验收指标**
| 指标 | 目标 |
|---|---|
| 越权访问拦截率 | **100%**（硬指标） |
| Faithfulness | ≥ 0.85 |
| 溯源可点击率 | 100% |
| 拒答准确率 | ≥ 90% |
| 审计日志完整率 | 100% |
| Prompt 注入拦截率 | ≥ 95%（20 条样本） |

### 7.3 Qdrant 生产后端 · 知擎·信创 Edge
**定位/目标用户**：政企/国企/数据不出内网机构（部署要求最高）。证明"断网可用、一键起、还能跑在信创环境"。

**数据**：复用 A/B 数据，只换部署形态，边际成本极低。

**功能**
1. 离线一体包：`docker compose` 一键起（向量库+推理+API）。
2. 断网可用：无外网依赖，断网自测通过。
3. 本地推理：Ollama/vLLM 起 Qwen3:14B（可换模型、可量化）。
4. 信创适配：昇腾 NPU + 麒麟 OS 的部署验证与性能数据（需在对应硬件环境下实测）。
5. 资源画像：不同硬件配置下的性能/显存数据（必须实测，不抄）。

**验收指标**
| 指标 | 目标 |
|---|---|
| 部署耗时 | ≤ 30 分钟（裸机到可提问） |
| 断网可用性 | 100% |
| 首 Token 延迟 | ≤ 1.5s（14B INT4，单卡 4090） |
| 量化精度损失 | ≤ 3%（对比 FP16） |

### 7.4 分层调度 · 知擎·调度 Router（可选扩展能力）
**定位/目标用户**：成本敏感客户。复刻技术能力"规则引擎+7B+72B 三层分工"，证明能把最贵模型调用砍半。
**功能**：规则/关键词 → 7B 轻模型 → 72B 重模型三级路由，按置信度升级，并发高峰自动降级。
**验收**：L2 调用占比 ≤ 30%；综合成本下降 ≥ 50%；准确率损失 ≤ 2%；P95 ≤ 3s。可在确有需要时分阶段推进。

## 8. 技术栈选型（逐层 + 算力）

| 层 | 推荐 | 备选 | 许可 | 本地算力 |
|---|---|---|---|---|
| L1 解析 | docling（主）+ MinerU（中文复杂表）+ PaddleOCR（扫描件） | MarkItDown / unstructured | Apache/MIT | OCR 阶段轻量 GPU，CPU 可跑 |
| L2 嵌入 | **BGE-M3**（dense+sparse 一体，混合检索免搭 BM25） | Qwen3-Embedding-0.6B/8B | MIT / Apache 2.0 | 568M，CPU 可跑、GPU 更快 |
| L3 向量库 | **Qdrant 单机 Docker**（payload 过滤支撑 B 权限） | Milvus / Chroma / FAISS / pgvector | Apache 2.0 | 几乎不吃，CPU |
| L4 重排 | **bge-reranker-v2-m3**（默认正确项） | Qwen3-Reranker | Apache 2.0 | GPU 友好，CPU 可跑 |
| L5 生成 | **Qwen3**（在线 API 演示 / 离线 Ollama-vLLM:14B） | DeepSeek / Llama / GLM | Apache 2.0 | 14B≈12–16G 显存（1×4090） |
| 编排 | **轻量自研 + Pydantic 配置驱动** | LlamaIndex 兜底 | — | 无 |
| 服务 | FastAPI（必做，工程能力证据）+ Streamlit（薄 UI）+ Docker Compose | — | — | 无 |

**算力总账**
| 阶段 | 本地算力 | 说明 |
|---|---|---|
| 开发期 / A、B 演示 | 可零 | 嵌入/重排/LLM 走 API，向量库用内存或云端 |
| 跑一次真实指标 | 不需要 own GPU | 同套 API 跑一遍记录数字 |
| Qdrant 生产后端 离线/信创 | 必须 | 3090/4090 跑 14B，或客户昇腾环境 |
| 最低可行配置 | 16G 内存 + 普通 CPU 笔记本 | 开发+接 API 跑通；本地跑 14B 再+24G 显卡 |

**商用授权**：BGE 系列（MIT/Apache）、Qwen 系列（Apache 2.0）、Qdrant（Apache 2.0）、docling（Apache 2.0）均可商用，无授权风险。

## 10. 演示与界面方案

- **可观测优先**：以可复现的评测脚本与真实指标为准（README + 代码结构 + 测试 + 评测 + 指标），界面只是辅助呈现。
- **已落地实现**：`web_demo.py` —— 单文件、零额外依赖的可观测控制台，统一覆盖三个模块，无需为不同模块重复搭建界面。
- **降级设计**：生成器支持 `stub` 模式，断网 / 无 API key 时仍可跑通检索、溯源、权限拦截与审计；真实 LLM 走完整链路，指标写入 `metrics_c.json`。**界面必须调用真实 pipeline，禁止写死答案。**
- **控制台能力**：检索透视（各阶段耗时 / 阈值判定 / 召回片段）、向量空间投影、点击引用直达 PDF 原文并高亮、内置评测台一键跑指标。
